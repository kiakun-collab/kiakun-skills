# Text Recovery

## 用户提供定稿时

用户直接给出标题、正文或指定文字文件且明确用于本次 PPT 时，该范围直接采用原文，记录 `userCopy[]` 的 id、page、text、source。无需再从图片 OCR、辨识伪字或发起第二轮文字确认；图片旧文案与定稿不同不是待解冲突。用户明确要求校对/润色时才按该要求修改，最终采用其确认的版本。

范围按页和对象匹配：只提供标题，正文仍需按来源读取；资料仅作背景或多个未定稿版本时，不能把其中任一份自动当定稿。来源不完整或对象对应确有歧义时只处理该疑点，已确定文字继续使用。

`rebuild_workflow.py bind-copy` 将对应抽取块锁定为 `textSource=user-provided`、`requiresTextRecognition=false`；保留从图片测得的 bbox 和样式。构建对象名称映射到该 ID，导出后 `user-copy-audit.json` 检查原生文字与定稿相同。仅忽略排版换行，不忽略标点、数字、单位和普通空格。它检查实现有没有错写，不重复判断用户文案是否正确。最终 PNG 仍检查漏字、出框、遮挡与可读性。

用户替换文案导致字数不同，不再按截图旧文案的字形宽度/行数评分；探针使用用户原文和实际文本框，只检查排版是否达标。用户未要求改写时不为了贴图而删字、润色或恢复旧标题。

## 未提供部分

先区分普通真实截图与 AI 生成的伪字。清晰截图文字可以直接转写；小字可一次带上下文放大或可用 OCR。不要把所有图都视为没有可靠文字。

AI 错字、乱码、伪字使用有来源的语义重建优先；不得通过裁剪或放大恢复原本不存在的正确字形。

## 证据顺序

1. 用户本次明确提供的定稿（已覆盖部分跳过图像文字恢复）。
2. 当前原 PPTX、可信业务原文、已确认术语和适用版本。
3. 图中清晰真实文字；OCR 仅是候选，数字、单位、负号/否定词需逐项核对。
4. 同页与跨页上下文，只用于提出候选，不能凭通顺度证明原文。

只登记异常项，准确文案提取一次后复用。AI 伪字可以给出有证据的唯一语义恢复，但数字、金额、日期、专名不能靠常识补写。

## 状态

- exact-source：逐字来源，记录路径/页/对象。
- observed-clear：普通截图清晰可见文字，记录区域。
- inferred-high-confidence：无逐字来源，语义和术语支持唯一候选，记录候选文字与依据；不能伪称 exact-source。
- ambiguous：多个合理候选，未经确认不得写成确定文案。
- unrecoverable：来源不足，保留待确认项。

异常项记 page、region、observedGlyphs、resolvedText、status、evidence、alternatives、needsHumanReview。置信度是描述，非概率。关键未决文字集中问一次，继续其余对象；不触发 Mode D。

文案复核回答“写什么”，最终 PNG 复核回答“是否完整可读”，不要在每次渲染时重新识别并改写内容。
